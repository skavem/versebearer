# versebearer

## Purpose
Wails3 desktop app for showing Bible verses and Christian song couplets on external screens during church services. Operator runs the Wails window (SvelteKit UI) to pick verses/songs/couplets. Picks are pushed to a separate "reciever" Svelte page via Server-Sent Events on `:9093`, which renders fullscreen text on projector windows. SQLite (GORM) stores Bible translations, books, chapters, verses, songs, and couplets.

## For AI Agents

### Working In This Directory
- Module path is `changeme` — do not rename without updating every `changeme/...` import.
- Four independent event channels: `bibleChannel` (verses), `songChannel` (couplets), `qrChannel` (QR toggle), `styleChannel` (visual style + fonts). The `broadcaster[T]` instances on `DbHandler` (`verseB`, `coupletB`) are the only producers for verse/couplet — they push to the channel AND emit a Wails event in one `.show(v)`/`.hide()` call. QR stays as ad-hoc `chan *bool` (different shape, only 2 callsites). `styleChannel` carries `*StyleEvent{Type, Target, Style, Fonts}` — produced by `Update*Style` / `Reset*Style` / `UploadFont` / `DeleteFont`. `sse.go:watchChannels` keeps a `lastVerseStyle` / `lastCoupletStyle` / `lastFonts` cache (seeded from DB on startup) so `sync` events include the current style without a DB hit.
- "Визуал" tab lets the operator customize verse and couplet projector styling independently (bg color/opacity, text color, font upload, border, padding, margin, text-shadow). Edits flow through `UpdateVerseStyle` / `UpdateCoupletStyle` (debounced 150ms in the UI), persist into the `GlobalState` row, and broadcast over `styleChannel` → SSE → receiver applies via `style:*` directives. See `backend/models/AGENTS.md` for the column layout.
- `broadcaster[T any]` (in `dbHandler.go`) is an unexported generic that owns: state pointer, channel, show/hide event names, and an `emit` callback. To add a new show/hide entity, construct another `broadcaster[YourType]` in `main.go` and wire it the same way as `verseB`/`coupletB`. Don't make broadcasters exported — Wails service reflection scans exported methods, not fields, so unexported is safe.
- `findByParent[T any](field, parentId, order)` (unexported package-level in `dbHandler.go`) is the generic GORM helper for child lookups. Each `getX` private method delegates to it. **Keep generics unexported.** Wails binding generation walks exported methods and needs concrete return types — exported generic methods would either fail to generate or produce `any`-typed JS classes.
- `main()` constructs channels and `DbHandler` *before* `application.New` then assigns `dbHandler.app = app` after — `app` is nil until then. The `emit(name, data)` wrapper on `DbHandler` guards `if g.app != nil` so it's safe to call during construction / tests without an app. Broadcasters take `dbHandler.emit` as a method-value callback (the binding picks up the assigned `app` once it's set).
- Wails v3 manager-pattern API in use: `app.Event` (`EventManager`), `app.Window` (`NewWithOptions` / `GetByName(name) (Window, bool)`). Do not revert to the pre-alpha.12 flat methods (`EmitEvent`, `NewWebviewWindowWithOptions`, `GetWindowByName`).
- `app.Event.Emit(name, single)` sets the JS `data` to `single` directly. JS handlers read `({data}) => ...`, NOT `data[0]`. Backend code that emits two+ args produces a JS array.
- **Window events have two separate subscriber maps, and they are not interchangeable.** `OnWindowEvent` appends to `w.eventListeners` (`webview_window.go:914`); `RegisterHook` appends to `w.eventHooks` (`:941`). Each event's delivery path consults only one of them. `WindowDidMove` / `WindowDidResize` / `WindowClosing` (used in `main.go`) go through hooks, but `handleDragAndDropMessage` (`:1404-1419`) iterates `w.eventListeners` alone — so `WindowFilesDropped` **must** be subscribed with `OnWindowEvent`. Registering it as a hook compiles, runs, and silently never fires. Cost us a "drag and drop does nothing, no error anywhere" bug; check which map an event's path reads before choosing.
- File drop is enabled by `EnableFileDrop: true` in `WebviewWindowOptions`, and only elements carrying the `data-file-drop-target` attribute receive drops. **On Windows the whole flow is JS-driven, not Go-driven**: the `@wailsio/runtime` listeners catch the browser's own `dragenter`/`dragover`/`drop`, call `preventDefault()`, and ship the real paths to Go via `chrome.webview.postMessageWithAdditionalObjects` (`webview_window_windows.go:2509-2522`). The Go-side `InitiateFrontendDropProcessing` → `window._wails.handlePlatformFileDrop` injection is for the other platforms. Consequences: the target is resolved as `document.elementFromPoint(x, y).closest('[data-file-drop-target]')`, so a drop zone works for its descendants too; the runtime toggles the `file-drop-target-active` class itself (project CSS only colours it); and the handler is registered by the runtime's index module, so importing `@wailsio/runtime` (not a deep path) is what wires it up.
- New Wails-exposed methods on `DbHandler` need `wails3 generate bindings` (`task common:generate:bindings`) to refresh `frontend/src/lib/bindings/`.
- Translation import (`db_import.go`) reads the JSON **on the Go side**: `PickTranslationFile` opens the native dialog, inspects the file and returns only path + counts; `ImportTranslationFromFile(path, name, shortName)` does the write. A full translation is ~6 MB — deliberately never sent through the webview bridge, unlike `UploadFont`/`UploadImage` which pass base64 for their much smaller payloads. `ImportTranslation(name, shortName, data []byte)` stays the byte-level core (what the tests drive).
- Import file layout: `{name, shortName, source, books:[{dividerBefore, name, fullName, content[chapter][verse]}]}`. A bare array of books (the original `Bible.json`) is still accepted — then the name must come from the caller. Empty strings inside `content` are verses the translation lacks: they are skipped on insert but keep the surrounding verse numbers correct, so `content` index +1 always equals `Verse.Number`.
- The whole import runs in one transaction — an aborted import leaves nothing behind. Duplicate translation **names** are rejected up front (there is no unique index on the column; the check is in `ImportTranslation`).
- `RemoveTranslation` refuses to delete the last remaining translation and hides the shown verse first if it belongs to the doomed translation. Deletion is manual cascade (verses → chapters → books → translation) because the models carry no FK constraints.
- Import/removal emit `translations_update` (no payload) and per-book `import_progress` (`{name, done, total, book}`). `BibleStore` reloads on the former; `TranslationsSettings.svelte` drives its progress bar off the latter.
- SSE port `9093` is hardcoded in `sse.go`. The projector windows open `http://localhost:9093` directly (`DbHandler.ShowScreen`).
- `couplet.Number` is the order field. `CreateCouplet` shifts all `>=number` up by one before insert **scoped to the same `song_id`** — the where-clause includes both `song_id = ? AND number >= ?` (a missing song_id filter was a real bug, fixed 2026-05-23). `RemoveCouplet` re-numbers `1..n` after delete. `UpdateCouplet` does NOT renumber — UI swaps numbers pair-wise via two `UpdateCouplet` calls for reordering.
- `ReplaceCouplets(songId, []CoupletInput)` is the bulk-edit endpoint: atomically deletes all couplets for the song and re-inserts the supplied blocks with fresh `Number = i+1`. Hides the active shown couplet first if it belongs to the song (all IDs change, so the old ref can't survive). Emits `song_update` once at the end. `CoupletInput{Label, Text}` is the wire type — exported so Wails bindings produce a TS class.
- Song CRUD: `CreateSong(number, title) *models.Song` — returns the created song so the UI can set it active without waiting for `songs_update`. `RemoveSong(songId)` — hides the active couplet first if it belongs to the deleted song, then cascades couplet delete + song delete + `songs_update` emit. No song-number renumber (numbers are free-form, not contiguous).

### Where user data lives (`backend/paths`, `backend/inits`, `main.go`)
- The SQLite DB, the Bleve index, and imported audio all live under one directory resolved by `backend/paths.DataDir()` — `%LOCALAPPDATA%\versebearer` by default. Setting `VERSEBEARER_DATA` before the process's first call into `paths` redirects the *whole* directory (DB + index + media), not just the DB — there is no way to sandbox only one of them. The value is cached in a `sync.Once` for the process lifetime; nothing resets it at runtime.
- `inits` has no package `init()` — the DB is opened by an explicit `inits.Open()` call from `main()` (first thing, before `application.New`) and from `backend/filler/fillDb.go`'s own `main()`. If `Open()` fails, `main.go` shows a native message box (`fatalDialog`, `fatal_windows.go`/`fatal_other.go`) describing what happened and what to do next, then exits — there is no silent fallback to a fresh empty database.
- **First run after this migration existed**: if a `test.db` from before the migration is found next to the program (CWD, then the exe's directory) and looks like our database (SQLite header + `verses`/`couplets`/`global_states` tables present), it's copied into the new location via `VACUUM INTO` and the original is renamed to `test.db.migrated` — never deleted. A file merely *named* `test.db` that isn't actually ours is silently ignored, not fatal; a candidate that can't be *read* at all, and more than one plausible candidate, are both fatal-with-a-dialog rather than silently skipped or guessed at. See `backend/inits/AGENTS.md` for the full algorithm and why each of those outcomes is what it is.
- `search.bleve` is **derived state** and does not migrate: the old copy next to the program (if any) is left alone (one log line noting it can be deleted), and a fresh index is built on the new location the normal way (empty → background rebuild, see below).
- **Known limitation, not yet fixed**: an installed build (Program Files, no `test.db` reachable in either candidate directory) finds nothing to migrate and silently starts with an empty database — indistinguishable from data loss unless the operator knows to look. The installer isn't in active use, so this hasn't been addressed. Also: rolling back to a pre-migration build after a successful migration launches an *empty* database (the old binary only knows to look for `test.db` next to itself, and by then it's `test.db.migrated`) — recoverable by renaming it back.

### Audio subsystem ("Звук" tab, `audio_*.go`, `AudioService`)
- `AudioService` is a second Wails service alongside `DbHandler` (both constructed and registered in `main.go`), not a method group bolted onto `DbHandler` — it owns its own player engine (`pl *player`, built on `github.com/gopxl/beep/v2` decoding + `github.com/gen2brain/malgo` output) instead of the GORM-only world `DbHandler` lives in. Full design/invariants are in `.omc/plans/audio-playlist-implementation.md` (concurrency rules И1–И6 at the top are load-bearing — read them before touching `audio_player.go`).
- Events (`AudioService.emit`, same nil-safe wrapper pattern as `DbHandler.emit`): `audio_tracks_update` (full library, after any import/delete/edit), `audio_playlists_update` (full playlist list with items, after any playlist mutation), `audio_track_changed` (carries a full `PlayerState` — emitted on `Play()` and on auto-advance, so the frontend doesn't have to wait for the next poll tick), `audio_stopped` (nil payload — track ended or was stopped with nothing to auto-advance to), `audio_device_lost` (nil payload — output device disappeared out from under playback), `audio_error` (string — background failures that have no synchronous caller to report to: gain measurement, a failed post-import DB write, a broken auto-advance), `audio_files_dropped` (`[]string` of real filesystem paths — see the drag-and-drop bullet below).
- `PlayerState` (`State()`, polled from the frontend every 500ms while the "Звук" tab is open — see `frontend/src/lib/stores/AGENTS.md`) never touches the DB and never blocks on the audio device — only on the player's own mutex, held no longer than one audio buffer's worth of work. `Peak` is read-and-reset (`atomic.Swap(0)`): the same call cannot report one peak twice, which the frontend's level-meter peak-hold has to account for.
- Imported files live under `paths.MediaDir`, named `<hash>.<ext>`; the DB row (`AudioTrack`) never stores the audio itself. A source format `beep` can't decode natively is converted to FLAC via an external `ffmpeg` process, looked up **next to the running executable** (`os.Executable()`'s directory, not `$PATH`) — see `build/AGENTS.md` for how it gets there (`fetch:ffmpeg` task, bundled into the Windows installer; not shipped on macOS/Linux).
- **There is no standalone "media library" screen.** The frontend "Звук" tab has a single view (playlists); `ListTracks`/`UpdateTrack`/`RemoveTrack` (`audio_library.go`) still exist and are still exercised by tests, but the only UI paths that import a file (`ImportTrack` button or a file dropped on the playlist, see below) add the resulting track straight to the currently active playlist in one flow (`PickAudioFiles`/dropped paths → `ImportTrack` per file, then one batched `AddTracksToPlaylist` call for everything that imported cleanly — not one `AddToPlaylist` call per file, which used to mean one full `audio_playlists_update` broadcast per file on a multi-file drop). Because of this, at least one playlist must always exist to have anywhere to import into — `backend/inits/db.go` seeds one ("Плейлист") on migration version 8 if none exist (`seedDefaultPlaylist`, idempotent by row count, not by version alone).
- **Deleting a playlist item is refcounted, not a hard delete.** `RemoveFromPlaylist` and `ClearPlaylist` (`audio_playlist.go`) both funnel through `deleteTrackIfUnused(trackId)` (`audio_library.go` — removing a track from the library is the library's job, not the playlist's, and it shares the `releaseTrackFile`/`refreshPendingAfterRelease` prologue-epilogue pair with `RemoveTrack` there): a track's file and `AudioTrack` row are only removed once no `PlaylistItem` anywhere references it any more (dedup-by-hash means the same track can legitimately sit in several playlists). `RemoveTrack` (`audio_library.go`) is the older, unconditional variant — it still deletes the row/file and cascades every `PlaylistItem` referencing it regardless of other references; nothing in the current UI calls it, but tests and any future direct-library tooling still can.
- **Drag-and-drop import** (`main.go` + `PlaylistPanel.svelte`): the main window is created with `EnableFileDrop: true`, and the playlist's item list carries `data-file-drop-target`. A drop fires Wails' `events.Common.WindowFilesDropped` on the Go side — `main.go` reads the real filesystem paths via `e.Context().DroppedFiles()` (a web `<input>` cannot get real paths at all) and re-emits them to the frontend as `audio_files_dropped`; the frontend (not Go) decides which playlist to import into, since "which playlist is active" is frontend-only state. `audioStore.handleFilesDropped` filters by extension client-side before attempting import (mirrors `audioFilePattern` in `audio_import.go`) so a non-audio drop fails fast with a clear message instead of hashing/copying an arbitrary file first. Wails auto-adds a `.file-drop-target-active` class to the drop target element while dragging — no manual `dragenter`/`dragleave` JS needed for the hover highlight (see `PlaylistPanel.svelte`'s `<style>` block). `WindowFilesDropped` is subscribed via `OnWindowEvent`, not `RegisterHook` — see the "two separate subscriber maps" bullet above; `main.go` shipped with `RegisterHook` here for a while (compiles, runs, drop silently does nothing) before that was caught and fixed.
- **Playlist reordering is button-driven (↑/↓), not drag-and-drop** — HTML5 DnD for reordering was removed (it conflicted with the file-drop zone above and operators found it flaky). One button pair sits to the right of the list (`PlaylistPanel.svelte`, mirroring `CoupletsList.svelte:69-144`'s side column acting on the active couplet) and moves whichever item `selectedItemId` points at — the same selection ArrowUp/ArrowDown drive from `Audio.svelte` — instead of a pair per row. It computes the swapped order locally and sends the whole thing through the existing transactional `ReorderPlaylist(ids)` in one call — unlike `CoupletsList.svelte`'s two sequential `UpdateCouplet` calls, which this deliberately does not imitate on the Go side even though the button placement/icons do.
- **Device selection is a modal, not a dropdown** (`AudioDeviceSelect.svelte`), listing every device with its supported sample rates/channels/sample formats (`AudioDevice.formats`, populated by `audio_devices.go`'s `deviceFormats`/`defaultListPlaybackDevices` — the latter falls back to `ctx.DeviceInfo` per-device when the plain `ctx.Devices` enumeration comes back with an empty `Formats`) and, for whichever device is actually open right now, the real negotiated sample rate (`AudioDevice.activeSampleRate`, from `player.openDeviceSnapshot`) — which can differ from what the device advertises as supported, since WASAPI shared mode picks one rate at open time. Picking a device (`pick()`) re-runs `refreshDevices()` afterward — the negotiated rate only exists once `ensureDevice` lazily opens the new device on the next `Play()`, so the modal would otherwise keep showing the previous enumeration's numbers.
- **State model (three independent pieces, not one hidden state machine):** playback (track/position/pause) belongs to `player` and is keyed by `itemId` + the already-open decoder — **not** by list position (`PlaylistItem.Position` is a display property of an element, never its identity). `pending` (`audio_autoadvance.go`) belongs to `AudioService` and answers exactly one question, "what comes after this item" — asked once at track start (for the fade-in-before-transition decision) and once at `done` (where to go next). `selectedItemId` (keyboard cursor) belongs to the frontend alone. **Playback stops only for a physical reason** — the file is about to be deleted from disk, the output device is changing, or the operator explicitly said stop — never merely because a playlist's *rows* were mutated (reordered/renamed/added to). `ReorderPlaylist` in particular never stops anything: position is not identity, so reordering cannot invalidate what's already playing.
- **`pending` is the only auto-advance mechanism, not a cache on top of one.** Every playlist mutation that can change the answer to "what comes after the currently-playing item" (`AddToPlaylist`/`AddTracksToPlaylist`, `RemoveFromPlaylist`, `ReorderPlaylist`, `SetPlaylistFlags`, a trim/gain edit via `UpdateTrack`) must call `AudioService.refreshPending`/`refreshPendingForPlaylist` — recomputes the answer and, only if it actually changed, reopens the decoder (`preparePendingNext`'s dedup check compares the desired next `itemId` against the one already held). `dropPending`/`dropPendingForTrack` (no recompute) are for the three physical-stop cases above plus a failed `Seek`. As a last-resort safety net, `tryAdvance` no longer treats an empty `pending` as "nothing to advance to": it falls back to `buildPendingSync`, a synchronous (blocking, full `decodeExt`) rebuild of the same answer — a missed `refreshPending` call anywhere costs a few hundred ms of gap instead of silence.
- **Deleting an `AudioTrack`'s file is the one case that's still allowed to stop playback**, and the decision lives *only* in `deleteTrackIfUnused`/`RemoveTrack` (`isCurrentTrack` check) — never in the item-removal call sites (`RemoveFromPlaylist`/`ClearPlaylist`). The reason is `os.Remove` sharing-violation on Windows while a decoder still has the file open, not "the row is gone" — so removing a *playing* item whose track is still referenced by another playlist does **not** stop anything; the track keeps playing to its natural end, it just won't auto-advance afterward (its `PlaylistItem` row, and thus `nextPlaylistItem`'s lookup of it, is gone).
- `AudioService.Play` is a no-op not just when the target item is already *playing* (И5) but also when it's already *loaded and paused* (`player.isCurrentItem`, not `isPlayingItem`) — a double-click/Enter on a paused row must not restart it from zero.

### Display keep-awake (`wake_windows.go`, `wake_other.go`, `db_outputs.go`)
- While at least one Output projector window is open, the app holds Windows' displays on — deliberately `ES_DISPLAY_REQUIRED`, not just `ES_SYSTEM_REQUIRED`: the latter only keeps the machine from sleeping, but Windows still blanks the monitors (all of them at once, including the projector) after the display-off timeout, which is the actual failure mode (a long verse on screen with nobody touching the mouse). This is tied to the projector window's lifecycle, not to audio playback.
- `golang.org/x/sys/windows` does **not** export `SetThreadExecutionState` or the `ES_*` constants (checked directly) — `wake_windows.go` loads it itself via `windows.NewLazySystemDLL("kernel32.dll").NewProc(...)` and defines its own `esContinuous`/`esSystemRequired`/`esDisplayRequired`.
- `ES_CONTINUOUS` is a **per-thread** flag: setting it from an ordinary goroutine works until the Go scheduler moves that goroutine onto a different OS thread, at which point the flag silently stops applying. `keepAwake()` therefore spins a dedicated goroutine pinned with `runtime.LockOSThread()` that lives until its `release()` is called, and clears the flag from that same thread.
- `openProjectorWindow` (shared by `ShowScreen` and `StartOutput`) is the single choke point for every projector window; it increments `DbHandler.wakeCount` on open and its `WindowClosing` hook decrements it, calling `keepAwake`/`release` on the 0→1 / 1→0 transitions (`registerOutputWindowOpened`/`registerOutputWindowClosed`). Because `main.go`'s main-window `WindowClosing` hook already closes every other window before the app exits, that same decrement path also covers app shutdown — there's no separate shutdown-time release call.
- `DbHandler.keepAwakeFn` is a test-injection point for the counter logic, same pattern as `player.openDevice` in `audio_player.go`: nil means "call the real `keepAwake`", tests substitute a call-counting fake so the counter transitions are verified without opening real windows or touching the Windows API (`wake_test.go`).
- `task dev` builds with **`DEV=true`** (set explicitly in `build/config.yml`), and that flag is what makes frontend hot-reload work at all. Without the `production` tag Wails compiles the dev branch of its assetserver, which reads `FRONTEND_DEVSERVER_URL` (set by `wails3 dev`) and reverse-proxies the frontend to vite. With the tag, that same function returns `""`, the window serves the `frontend/dist` embedded in the binary, and Svelte edits only appear after a Go rebuild. `DEV` defaults to `"false"` in the root `Taskfile.yml`, so every release path — `task build`, `task package` — is production unless someone asks otherwise. The same variable doubles as the app's own dev switch: `task dev` exports it so the receiver is served from `reciever/dist` on disk instead of the embedded copy.
- **`CGO_ENABLED: 1` is load-bearing in every platform Taskfile.** The SQLite driver is a cgo wrapper; the upstream beta.5 templates default it to `0`, and adopting that verbatim would break the build. Watch for this whenever build assets are re-synced with upstream.
- **`build/` is laid out per platform** (`build/windows/`, `build/darwin/`, `build/linux/`, each with its own `Taskfile.yml` and assets) — the beta.5 layout. `wails3 update build-assets` regenerates the generated files (`info.json`, manifests, plists, nfpm config) but never touches the Taskfiles, so local edits there survive. Three edits are ours and would be lost in a naive re-sync from the upstream templates: the `reciever` tasks, the bindings output directory (`frontend/src/lib/bindings`, not the default `frontend/bindings`), and `CGO_ENABLED: 1`.
- **Vite must listen on IPv4, on every platform.** Wails' dev proxy forces a `tcp4` dial whenever the dev-server host is `localhost` or `127.0.0.1`, and that override carries no build tag. Vite defaults `server.host` to `localhost`, which resolves to `::1` first on Windows — the mismatch surfaces as `HTTP ERROR 502` in the window and `dial tcp4 …: connectex` in the log. Hence `server.host: '127.0.0.1'`. Wails' own "Connected to frontend dev server!" check does *not* catch it: that probe uses a plain client and reaches the server over IPv6.
- **HMR bypasses Wails.** The page loads from `wails.localhost` (Wails rewrites the start URL to carry the vite port), but Wails cannot proxy a WebSocket upgrade — it has no `http.Hijacker` — so `server.hmr.host` points the client straight at vite. Leave `hmr.port` unset: vite reuses its own port, which is configurable via `WAILS_VITE_PORT` / `wails3 dev -port`, and hardcoding it makes HMR die silently whenever the port is overridden.
- **The dev watcher does not actually fire — restart `task dev` after Go changes.** `dev_mode.watched_extension` lists `*.go`, but measured against a live watcher it rebuilt neither on an mtime touch nor on seven real `.go` edits over twenty minutes; the run's only build was the initial one. Frontend edits are unaffected — those come through vite. (Note also `dev_mode.git_ignore` in `build/config.yml` is a dead key: the watcher library reads it as `git`, so the line is silently dropped. Harmless while `watched_extension` acts as a whitelist.)

### Full-text search (`backend/search`)
- The index is **derived state**: everything in `search.bleve` can be rebuilt from SQLite. `openSearchIndex` (called from `main` *after* `dbHandler.app` is assigned, so progress events aren't swallowed) rebuilds in a goroutine whenever the completion marker (`<index path>.complete`) is missing — **not** whenever the document count is zero: `RebuildSearchIndex` calls `Reset()` before refilling, so a program closed mid-rebuild leaves a non-empty-but-incomplete index that a count-based check would never retry. The marker is removed at the start of a rebuild and written only after it finishes successfully. `RebuildSearchIndex` is also exposed to the UI.
- **Russian morphology is done by symmetric expansion, not lemmatisation.** `gomorphy` has no lemma API — only `WordForms`, and it is *not* invariant to the input form: `WordForms("любовь")` misses "любви" while `WordForms("любви")` contains "любовь". So every word is expanded into the snowball stems of all its word forms, on **both** sides — at index time and at query time — and a match is a non-empty intersection. Any change that expands only one side silently breaks the most common words. See the package doc in `morph.go`.
- Words outside the OpenCorpora dictionary (proper names, «рече», «глаголющий») degrade to plain stemming rather than disappearing. Suppletion across *derivation* («говорить»→«сказал», «верить»→«уверовал») and Church-Slavonic archaisms are **not** covered by design — that needs a synonym dictionary, which the project deliberately doesn't have.
- Two fields per document: `morph` (expanded stems, the actual retrieval field) and `text` (normalised original, used only for the exact-word and exact-phrase boosts). Both are non-stored — result text is read back from SQLite by ID. Without those boosts ranking is visibly wrong: OpenCorpora puts participles in the verb's paradigm, so «возлюбил» ties with «возлюбленному».
- Bleve analyzers register via **blank imports** (`analysis/analyzer/simple`, `.../keyword`). Dropping them fails at index *creation* with «no analyzer with name 'simple' registered».
- `search.Match` offsets are in **UTF-16 units** — the same count JS slices by. Not bytes and not runes: couplet text is operator-authored, and one pasted emoji is two UTF-16 units to one rune, which would shift every later highlight in that couplet and cut through a surrogate pair. `TestHighlightAfterAstralChar` pins this. Highlighting is computed in Go (`Highlight`) rather than by Bleve's highlighter, because the index holds stems and Bleve would highlight «возлюб» instead of the live word.
- `Normalize` applies NFC before casefolding: the Open Bible stores «й»/«ё» decomposed (и + U+0306), and without it plain Russian queries miss visually identical text. Never normalise a whole text before computing offsets — NFC changes string length and shifts every following position.
- **Any new couplet mutation must call the index hooks** (`indexCoupletSilent` / `unindexSilent` / `reindexSongSilent`), and any that deletes rows must collect the ids *before* deleting. The hooks are deliberately silent: a stale search row must never fail the operator's actual action. Never index a record whose write failed — a document keyed on id 0 is unreachable by any later delete and only a full rebuild clears it.
- **Bulk index writes and deletes both go through batches** (`PutBatch` / `DeleteBatch`, `indexBatchSize`). Each single-document Bleve call is its own segment commit, so the per-id loop that removing a translation would otherwise run costs minutes of pinned disk for ~31k verses.
- `indexTranslationSilent` takes `rebuildMu` (blocking, unlike `RebuildSearchIndex`'s `TryLock`): the first-run rebuild runs for seconds in the background, and an import landing inside that window would otherwise write documents that `Reset` then destroys — leaving the new translation unsearchable with nothing logged.
- A rebuild that fails must emit `search_index_failed`. The UI derives "building" purely from events, so without it the in-input spinner and the disabled rebuild button stay stuck until restart.
- `indexAllCouplets` re-checks the id list against the DB after writing. A couplet deleted mid-rebuild has its unindex hook run against a document that does not exist yet, and the already-snapshotted batch then writes it back permanently. **Known gap of the same shape:** deleting a *translation* during a rebuild has no such reconciliation — its verse ids are gone from SQLite by then, so nothing can enumerate the stale documents. The cure is a second manual rebuild.

### Testing Requirements
- Go smoke tests live in `dbHandler_test.go` (in-memory SQLite, no Wails dependency thanks to `emit` nil-safety). Run via `task test`, which sets `VERSEBEARER_DATA` to a repo-local `tmp/test-data` before calling `go test -race ./...` — the env var keeps every test's `paths.DataDir()` (and therefore `MediaDir()`) pointed at a throwaway directory instead of the real `%LOCALAPPDATA%`; the primary defense is simpler, though — `backend/inits` has no `init()`, so a bare `go test ./...` typed by hand never opens any database unless a test asks for one explicitly. Cover: `GetTranslations` preload depth, `CreateCouplet` song-scoped renumber, `RemoveCouplet` 1..n renumber.
- `backend/paths` and `backend/inits` tests never touch the real `%LOCALAPPDATA%`: `paths` tests reset its package-level `sync.Once` guards and point `XDG_DATA_HOME`/`VERSEBEARER_DATA` at `t.TempDir()`; `inits`'s migration functions (`migrateLegacyDB`, `OpenAt`, …) take every path as an explicit parameter instead of asking `paths` for one, specifically so they're testable this way.
- Search tests live in `backend/search/search_test.go` (temp-dir Bleve index, no SQLite). They pin the behaviours that are easy to break silently: symmetric expansion on «любовь»/«любви» and «человек»/«людей», rune-based highlight offsets, exact-form ranking, translation/kind filtering, layout and typo fallbacks. `TestArchaicFormsAreNotLinked` records a known limitation rather than a bug.
- Audio engine tests live in `audio_player_test.go` — the first concurrent subsystem in the project, so it and every other `go test` invocation here must run with `-race` (`go test -race ./...`), not just plain `go test`.
- `wake_test.go` covers the output-window-count → `keepAwake`/`release` transition logic via `DbHandler.keepAwakeFn` (fake, no real windows) plus one smoke test that the real Windows `keepAwake()` tolerates a repeated `release()`.
- Manual UI: `wails3 dev` or `task dev` and exercise the five tabs (Библия, Песни, Экраны, Визуал, Звук) + projector.
- Frontend type-check: `cd frontend && npm run check`.
- Reciever type-check: `cd reciever && npm run check`.

### Common Patterns
- Wails bindings live at `frontend/src/lib/bindings/changeme/...` — autogenerated, do not hand-edit.
- Go side uses uppercase exported method names; the binding gen produces matching TS functions.
- All public `DbHandler` methods that take numeric IDs use `float32` because the Wails JS bridge serializes JS numbers as float — cast to `uint` inside.
